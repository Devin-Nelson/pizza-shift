# Dominus Pizza (Roblox)

Roblox pizza job game turning tycoon/simulator: a spiritual successor to "Work at a Pizza Place". Every station is a skill minigame on a 3D pizza; each player opens their own store on a lot (or joins one, up to 4 players) and hires NPC staff to run it with them. Store operations are modeled on a delivery-first pizza chain (Domino's-style) **under our own brand**. Never use a real chain's name, logo, or trade dress; it would risk a Roblox IP takedown. Goal: ship ASAP, then monetize (game passes) and polish.

## Workflow
- Rojo 7.7.1 lives at `%USERPROFILE%\.rojo\bin\rojo.exe` (not on PATH). The Studio plugin is installed.
- Live sync: `rojo serve` in this folder, then Connect in the Studio Rojo plugin. Build check: `rojo build -o test.rbxlx`.
- Checks (binaries from the luau-lang/luau GitHub release, kept in `~/tools/luau`; Temp gets cleaned): `luau-compile --null <file>` for syntax; `luau-analyze <file>` for lint (ignore Roblox globals/types it doesn't know; look for Unused/Shadow warnings and any unknown global that isn't a Roblox built-in). Only Studio playtesting catches runtime errors, so ask the user for Output-window errors or screenshots.
- More checks, from the repo root (tools in `~/.rokit/bin`): `lune run tests/specs` (headless specs: loads the real Config, GameClock, SalesPlan, Style, TicketRows, Staff, Follow and DataService (fake DataStore for the save lock) with stubbed engine globals; add a spec for every new pure rule) and `selene src` (must stay at 0 errors, 0 warnings). StyLua isn't used: the code's long-line style isn't stylua's.
- Studio MCP notes: every `execute_luau` call resets the camera to Custom (so a station's camera can't be inspected live: rebuild it from `Config.StationView` instead), the viewport can report 1x1 while Studio isn't rendering, and screenshots can time out mid-run (a minigame session then times out at 120 s).
- Station meshes (Blender, 2026-10-20): `tools/blender/<station>.py` builds each station parametrically in Roblox art-local studs (sizes from `StationArt.Layout`, one mesh per Roblox material, instanced pieces at the origin) with the shared `kit.py`; `blender -b -P tools/blender/<station>.py -- --render` writes `~/Roblox-Assets/models/dominus/<station>/<station>.glb`, a `.json` of each mesh's size and centre, any textures, and preview renders (the user approves the render before upload). Upload with the roblox-3d-model skill's `scripts/upload_asset.py` run by **Blender's Python** (`C:\Program Files\Blender Foundation\Blender 4.5\4.5\python\bin\python.exe`: the system Python has no `requests`): the .glb as `Model`, textures as `Image`; load `ROBLOX_API_KEY` / `ROBLOX_USER_ID` from the user scope into that process (PowerShell `[Environment]::GetEnvironmentVariable(..., "User")`), never print them. Then `game:GetObjects("rbxassetid://<model>")` in Studio (edit mode) gives one MeshPart per mesh: copy each `MeshId` (the inner id) into `src/server/MeshBank.luau` with the `.json` size and centre. The importer turns the model 180 degrees about Y (StationArt's `IMPORT_TURN` undoes it); sizes come in 1:1. Store positions the models must meet (where the dough table, corner table, sauce table and makeline join) live in `tools/blender/layout.py`; the sauce script runs clearance checks on every build (`[check]` lines, the build fails on any clip) and prints the numbers `StationArt.Layout.SauceTable` copies (`[layout]`). In Studio edit mode a `require` stays cached for the session: to preview StationArt after editing MeshBank, clone both modules into a temp folder and require the clone. A camera tuple may carry a fifth value, `clip_start`, for a cutaway render (the ovens' `hood_section`).
- Studio MCP (server "Roblox_Studio") can run playtests: `start_stop_play`, `execute_luau` on the Server/Client datamodels, `get_console_output`. A scripted run fires the real remotes from the Client datamodel (the server's validation and min-time checks still apply) to drive every station headlessly. The mouse/keyboard input tools use GUI coordinates (no top-bar inset); Studio stopped rendering partway through one clicked run, so save clicked/recorded runs for milestones.
- The map is built entirely in code; MapBuilder deletes Studio's default Baseplate/SpawnLocation on start (the Baseplate z-fights with our grass).
- If Studio shows something the code no longer does (e.g. old station labels), the Rojo plugin has disconnected and Studio is running stale scripts. Reconnect before testing.

## Architecture
- `src/shared/Config.luau`: all balance, stations and the make steps, the menu (sizes, toppings, prices, portions), brand, clock and sales tuning. Change numbers here first.
- `src/shared/Remotes.luau`: RemoteEvents (server creates, client waits).
- `src/shared/GameClock.luau` + `src/server/ClockService.luau`: 24h clock (ReplicatedStorage "WeekHour" attribute, 0-168 from Monday 00:00), sun, `Closed` event at midnight. `GameClock.hoursText()` builds hours text from Config.
- `src/shared/Pizza3D.luau`: 3D pizza builder used by client minigames and the server's oven/belt visuals (same seed = same layout).
- `src/server/MapBuilder.luau`: map, store layout (`BuildShop`, plan v4.1 in `docs/floorplan.svg`), houses (16), store lots (5, empty until a store opens; a plot is 60 x 136 with its sign out front, the store's parking lot is behind it at z -62). `StationArt.luau`: station visuals; a Model in `ServerStorage/StationModels/<Kind>` overrides the generated art. A station in `MeshBank` is built from its Blender meshes (`stationMeshes`: one `CreateMeshPartAsync` template per mesh id per server, cloned by `M`); if any mesh fails to load it gets the code-built art instead (kept as the fallback). Big Metal meshes use `STAINLESS` (140, 145, 152): the lighter `STEEL` blows out white under the store's lights. `StationArt.Preload()` (Main, at server start) loads every MeshBank mesh in parallel: without it the first store took 10 s to open, with it 0.1 s. `StationArt.Screen(size, cf)` makes a pizza screen sized to its pizza (diameter + 0.06 rim; the wire-mesh Blender screen once the sauce corner's meshes have loaded, else a disc); ShopService uses it for the skin racks and the ready rack.
- `src/server/ShopService.luau`: order flow from the sales forecast (walk-in/phone/online, 1-30 pizzas), dough skins on two 15-slot screen racks at the sauce station (30 slots, any sizes, oldest of a size used first), dough trays on the stretch table (`shop.trays`: per size, the `DoughBall` Indexes still there; `takeBall` on every stretched skin takes the ball the player clicked (`payload.ball`), or for staff the highest left, and refills an emptied tray to `Config.Dough.TrayBalls`; `updateTrays` hides the used ones), and a free-form make process: **pies** (physical pizzas, `shop.pies`) are made without an order (Sauce picks any skin size → "Sauced" → Cheese → "Cheesed" → Toppings → "Ready" on the 15-slot ready rack, `readySlot`; a toppings job only starts if `readyRoom` has a slot for it), and `loadPie` puts one in the next free oven slot (round-robin 1-6, waits for the lane entrance to clear) and matches it to an order **ticket** (`matchTicket`: auto, or the order the player picked; none = an extra). Toppings are scored and paid at load time. `ovenStep` (10 Hz) moves pies along their lane in real time (`Config.Oven.BakeTime`), browns them between the chamber mouths (`Pizza3D.bakeTint`), makes them pullable ("Exit") the moment the leading edge clears the exit mouth, backs them up at the end of the belt and drops the front one `FallAfter` seconds after it reaches the end. The oven tender pulls any pie that is out (Cut session; putting it down returns it to its lane), boxes it; when every ticket of an order is boxed the order goes to carryout or the heat rack. Carryout (the user, 2026-10-21): every customer has a name (`Config.CustomerNames` + a last initial, "John P."; they say it when their order's rung in); a boxed carryout order goes onto the carryout rack (`shop.carryout`, `Config.Carryout.Slots` = 6 stacks, two a tier, a queue past that) as a stack of boxes with a name tag, and its customer steps up to the counter by the warmer saying "Pickup for John P.!" (`atCounter`; they give up after `PickupPatience`, a lost sale). A player clicks the stack to carry it (`Carrying` attribute), clicks the customer to hand it over (anyone else says "That's not mine - I'm ..."), or clicks the rack to put it back; Register staff hand orders over too (job `Handoff`). Online orders nobody came in for still complete on their own. Deliveries (the user, 2026-10-21): boxed delivery orders go into hot bags labelled with the order number (bags modelled later), waiting on a delivery ready rack by the dispatch station, where drivers check out. Built (2026-10-21, spot C on the user's plan: along the right wall past the carryout rack, the rack toward the walk-in): the dispatch station is the "DeliveryRack" station (the id predates it: staff stats are saved under it; label "Dispatch"), `tools/blender/dispatch.py` (a 5.0 x 2.4 table, the overhead shelf, the monitor dead centre of the opening at chest height, a touch screen later); its `DispatchScreen` lists the deliveries waiting; the delivery ready rack is the carryout rack's model (`Builders.DeliveryReadyRack`, `DeliverySlot_1..6`), each waiting delivery order on it as a placeholder red bag labelled `#<order>` (`ShopService.layoutBags`, run by `updateBoards`); drivers still pick from the tickets and the bag leaves the rack. Load time = placed → last pie loaded; total time = placed → last pie boxed. Stock, open hours, **server-authoritative** scoring and pay, management slots.
- `src/server/SalesPlan.luau`: weekly forecast, day/daypart split, order-size rolls, pricing. `CarService.luau`: per-driver cars, network-owned by the driver. `DataService.luau`: DataStore saves (profile `Staff` = the player's hires).
- `src/server/StoreService.luau`: the 5 store lots (MapBuilder; lot 1 is the old HQ site, stores are built when opened). Store picker (`OpenStorePicker` / `ChooseStore` / `RequestStores`), membership (`ShopService.SetMember`, player attributes `StoreId` and `StoreOwner`, max `Config.Store.MaxPlayers`), owner handover (longest-serving member, store rebuilt as theirs), and the Staff menu (`RequestStaff` / `HireStaff` / `AssignStaff` / `ScheduleStaff` / Studio-only `GrantStaff` -> `OpenStaffMenu`; owner-only changes; `assign` moves a team member or toggles a manager's station; `prepareStaff` sanitizes the owner's saved staff once as their store opens; changes push with `ShopService.SetCrew`).
- Staff rules live in `src/shared/Staff.luau` (pure, specced): shifts (`shiftAt`: the sales dayparts, Lunch starting with prep at 9:30), station levels and XP (`xpToNext`, `addXP`), what a level does (`quality`, `speed`), call-outs (`calloutChance`), managers' Flexibility (`stationLimit`, `overload`, `jobQuality`, `jobSpeed`), new hires (`newMember` from `Config.StaffGen`), save repair (`sanitize`), the roll (`rollKind`). Hired staff at work live in ShopService ("Hired staff (NPCs)" section): `shop.crew` holds each member's saved record (XP is written straight into the owner's profile), `startShift` rolls call-outs as a shift begins and `crewRoster` brings in whoever's scheduled; `crewStep` ticks once a second (`crewStart` looks for work across a member's stations, `crewJobAt` / `crewFinish` / `releaseCrew`). Every station step's core is one shared function (`saucePie`, `cheesePie`, `topPie`, `pullPie`, `boxPie`, `loadPie` with `player` nil) called by both a player's minigame result and the staff, so the rules can't drift. Staff only sauce/top what open orders still need (`neededSize`, `neededToppings`, `doughNeed`), stretch needed sizes first, and only load exact topping matches; at the heat rack they drive (walk to the driver door, vanish for `Config.StaffWork.Trip` x their speed, complete the order). NPCs are tagged `CrewNPC`; the client hides one standing where its player works (Workstation). Delivery orders need 2+ players or someone on shift with the heat rack among their stations, else they arrive as carryout (`takesDeliveries`).
- Staying at a station: every Config.Stations station is a `stay` station (Register, Dough, Sauce, Cheese, Toppings, Load, CutTable, DeliveryRack), server-tracked (`stationed` in ShopService). `useStation` is the single entry point (prompts, `UseStation(station, pickId?)`, `Follow`); `enterStation` fires `StationMode` to the client, then `assign` starts the next job there (also every tick and `Config.NextJobDelay` after each step, longest-waiting player first) or sends a `StationStatus` "waiting for..." text. `pick` stations (Load, CutTable, DeliveryRack) never auto-start: `startStation` needs a pickId (the exit pie / the order); at Load it only ever returns a status, loading goes through `LoadPizza` (or a follower's auto-load). A delivery doesn't hold the station (`holdsStation`): taking one takes you off it. `startStation` returns nil when a job started, else that reason. `LeaveStation` / X / Exit leaves; a session timeout while stationed also leaves (AFK guard). `LoadPizza(pieId, orderId?)` loads from the ready rack (only while stationed at Load; orderId 0 = extra, nil = auto); the toppings minigame's Load loads straight from its result (in Pick mode the order picker opens first, over the minigame).
- Following (the default, user 2026-10-19): a player in the make process follows the top pizza. `stepDone` takes a follower straight on with their pizza to its next make step (unless that station is `manned`: a parked player or staff there); otherwise `assign` asks `followTarget` (state gathered in ShopService, the decision in the pure, specced `src/shared/Follow.luau`): the oldest ticket nobody covers yet -> its pizza already on the line (go work it), else its skin on the rack (Sauce, size set), else stretch it (Dough, size set); nothing on order = stretch ahead, any size. A set size rides in `Stay.size` -> `startStation(..., size)` -> `data.size` (the client skips the size tiles; the server checks the result's size). A follower sent to Load with a pizza loads it at once (auto-match). Covered = pies claimed or at a manned station, other followers' Dough/Sauce sessions (`data.size`), staff jobs; `freeSkins` leaves out skins a follower is saucing. Picking a make station from the HUD (`UseStation`) parks you there (`parked`, player attribute `Following` = false; the old move-back rule still applies to parked players); a prompt at a make station or the HUD's Follow key (`Remotes.Follow`) follows again; joining a store resets to following.

## Conventions
- Stations are invisible hitbox Parts with a `Station` attribute and a ProximityPrompt; art is parented underneath. Gameplay code finds things by name and attribute, never by appearance.
- Never hard-code store hours or staff kinds: use `GameClock.hoursText()` and `Config.Staff` / `Config.StaffOrder`.
- Shop-local coordinates: entrance faces +Z; Roblox's Front face is -Z (SurfaceGuis facing the street use `Back`). Station art: LookVector points at the worker.
- The client reports raw inputs only; validate every remote payload on the server.
- Road/lot surfaces are `CanCollide = false` so the car (it rides on four welded, low-friction cylinder "wheels") doesn't snag on seams. The car is hollow and sized for a seated character; only its lower body, bumpers and wheels collide, and exiting puts you beside the driver's door.
- Printed box lids are Front faces on parts laid flat with `BOX_FLAT` (Top-face SurfaceGuis read upside down from the front).
- Minigame input: Space / gamepad A, left click, or tap all count as the action button (`bindPress`); holds use mouse/finger on the 3D view.
- The DataStore key is still `PizzaShift_v1` (pre-rename); changing it orphans saves.
- Saves are session-locked (`DataService`: `claim` on load, `Save` only while this server holds `Lock`, `Release` lets go; `Config.Save`); never write player data with `SetAsync`. Specced in `tests/specs.luau`. Carryout patience is 300 s (fix from the 2026-10-19 audit, user-approved).

## Game design decisions (from the user)
- Direction (2026-10-19): moving from roleplay toward a tycoon/simulator. **No clock-in and no roles**: every player can work every station and deliveries. **No supply truck for now** (user, 2026-10-19 #2): stock refills itself to full every 20 s (`Config.Shop` StartingStock = AutoRestockAmount = MaxStock), so it never runs out; the stock code stays for when the truck returns. On joining, a player opens their own store on a free lot or joins an occupied one (up to 4 players, open to anyone; an owner lock may come later). 5 lots per server (lot 1 = the old HQ site). When the owner leaves, the longest-serving player takes over and the store reloads as their saved store (their staff); nobody is kicked.
- Delivery orders only come in with 2+ players at the store or a hired driver; otherwise those orders arrive as carryout (user's call).
- Staff (user's choices, 2026-10-19): a Staff menu from the start. **Team members** (bought, capped at 3 for now) work one station each, including the heat rack (driving). **Assistant and Store Managers** (from the roll; Studio-only grant for now, `GrantStaff`) can work several stations; **Flexibility** (managers only) sets how many before they're overwhelmed, and past that every job of theirs is slower and sloppier, so orders back up and sales are lost. Everyone has a **stat per station** (a level, raised by XP from jobs done there; each level makes them faster and better there), **reliability** (chance to call out of a shift: they miss it and the owner is told) and **availability** (which of the 3 shifts, Lunch / Dinner / Late Night, they can work; all 3 = "open availability", rare and sought after). The owner schedules who works each shift within availability. Buying (200 coins, rising) hires a random basic team member; rolls/spins (not built) will give better odds of high stats, open availability and managers. Ready for the roll: `Config.StaffRoll` (odds, cost, `Enabled = false`), `Staff.rollKind`, `Config.StaffGen` pools per kind, the menu's "Coming soon" row. Open: duplicates, what else managers do, coins vs Robux, the roll's team-member stat pool.
- Money: everyone keeps per-task pay and tips; the owner also earns `Config.Store.SaleCut` of every completed sale at their store (NPC-made too) and `OwnerRoyalty` on other players' pay.
- Menu (user, 2026-10-19, tentative): no specialty pizzas. A pizza is a size plus up to 3 toppings (`Config.MaxToppings`), each listed on its own ticket line; price = size + a price per topping (`Config.ToppingPrice`, Claude's numbers). Orders are `{ size, toppings }` (SalesPlan `rollToppings`, `name`, `describe`).
- Portions: by size and topping count (1 / 2-3), from the user's portion chart (2026-10-19 #2; it also covers 6"/16", 4+ toppings, Philly, bacon, sausage, beef, chicken, tomato, onions, jalapeno/banana peppers and alfredo, none of which the game has: keep the current six toppings and three sizes). Groups: pepperoni = ham (pieces, S 20/16, M 30/24, L 40/32); pineapple = mushrooms (oz, 2.5/1.5, 3.5/2.5, 5/3.5); peppers = olives (oz, 1.5/1, 2/1.5, 3/2). Cheese 3.5 / 5 / 7 oz. Weighed toppings go on by the piece (`Config.CountedToppings`, `Config.PieceOz`: each piece put on weighs that much, so the client still reports piece counts). ±10% variance is allowed; beyond that, customer satisfaction drops (`Config.PortionFactor`).
- Pizza sizes are real proportions (10"/12"/14", `Config.PizzaInches`); 3D pizzas, dough skins and boxes all scale from them.
- Hours: open 10 AM to midnight every day; stations open at 9:30 AM to prep; at midnight everyone is sent off their station and the board is cleared. Players can explore any time.
- Sales: weekly $25k-$30k; Mon/Tue/Wed 10% each, Thu/Sun 15%, Fri/Sat 20%, each jittered ~3%; dayparts 10-4 = 20%, 4-9 = 70%, 9-12 = 10%. Orders are generated against that dollar budget, so order count follows the (daily-randomized) average ticket. Order sizes: small 1-4 pizzas (common), medium 5-15 (less common), large 15-30 (rare). Times in real minutes: load time = placed → all pizzas in the oven; total time = placed → all pizzas boxed.
- Tips scale with the order total: delivery tips go to the driver; carryout ("insider") tips are lower and split among the crew.
- Every dollar is a real order (user, 2026-10-19): there is no off-screen crew. Every forecast order comes to the store (a full lobby takes carryout online). Every order has a patience timer (`Config.OrderPatience`: 5 min + 75 s per extra pizza; walk-ins leave, phone/online/delivery orders are cancelled); what isn't done in time, goes to a wrong house, or is still open at midnight is a lost sale (`loseSale`, `sales.lostToday`, "LOST TODAY" on the sales board). Forecast = sales + lost + still open.
- Playtest (the user, 2026-10-23): `Config.Playtest.FreeManager` gives every store owner without a Store Manager a free one as their store opens (`prepareStaff`): open availability and scheduled for every shift, Flexibility 10/10, reliability 10/10 (never calls out), on Register + Dispatch (Claude's call: so a solo tester gets deliveries; the owner can move them). Saved like any hire, so once per player; turn it off when the roll goes live. Carryout on touchscreens: only a tap (under 0.4 s, under 12 px) picks up, hands over or puts back an order (`CarryoutPicks`), aimed where it landed: a camera swipe starting over the rack used to put a just-picked order back. Every tap pick (dough balls, topping pans, oven pizzas, boxes, bubbles) aims with its own input (`Workstation.pointerRay(input)`): the remembered pointer could still be the last tap, so every pick took two taps on mobile.
- Claude's calls on staff (tunable in Config, not the user's): price x1.25 per hire; at most 2 Assistant and 1 Store Manager; 8 on a shift; levels 1-20 (quality 0.5 -> 0.95, job time x1.5 -> x0.6); bought hires start at level 1-3 everywhere, reliability 3-8, available for 1/2/3 shifts at 50/40/10%; Assistant Managers level 3-6, reliability 5-9, Flexibility 2-6; Store Managers level 5-9, reliability 7-10, Flexibility 5-10; Flexibility F handles 1 + F // 2 stations (1-6), each one past that +50% job time and -15% quality; call-out chance 3% per reliability point short of 10; managers step between their stations without walking; staff don't sauce or top ahead of demand (dough is prep); staff walk straight through counters (no pathfinding).
- Multiple locations with different volumes and sales dynamics are planned but not designed yet (`AddShop(..., volume)` exists).
- Brand: the user chose "Dominus Pizza" after being warned it is close to "Domino's" and could draw a trademark claim. It's a single value, `Config.GameName`.
- Make process: every pizza physically exists at every step (skins on racks, sauced/cheesed pizzas waiting on the make-line, oven belt). Each step is its own station; players can work one station repeatedly (e.g. sauce 5 in a row) or follow one pizza start to finish via HUD buttons. Player autonomy and time management matter more than forced flow. In first person the player's hands are invisible (only tools show).
